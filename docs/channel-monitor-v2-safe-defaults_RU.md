# Безопасные настройки Channel Monitor V2 и щадящее заполнение истории

[English](channel-monitor-v2-safe-defaults.md) | Русский

**Дата:** 2026-08-08
**Статус:** одобрено к реализации
**Ветка:** `fix/channel-monitor-v2-ops-ui-blockers` (поверх channel-monitor-v2)

## Проблема

1. **H2** — миграция 195 и значения по умолчанию в коде задавали `channel_monitor_mode=v2`, поэтому любое обновление без существующего ключа автоматически включало пассивный V2, останавливало проверки V1 и могло оставить пользователей с пустым экраном V2.
2. **M1** — первичное заполнение истории принудительно запускалось каждые 5 секунд и обрабатывало диапазон до `now-30d` фрагментами примерно по 24 часа через `RecomputeRange`, создавая чрезмерную нагрузку на основную БД.
3. SQL-дедупликация ошибок сопоставляла `request_id` без ограничения по `created_at`, из-за чего ветка `candidate_ids` сканировала историю `ops_error_logs`.

## Решения

| Тема | Решение |
|------|---------|
| Режим по умолчанию | **v1** (сохранить активные проверки). V2 включается явно. |
| Существующие строки `channel_monitor_mode=v2` | **Не изменяются** (`ON CONFLICT DO NOTHING`; без принудительной перезаписи). |
| Переключение на v2 | Для `fire()` и `RunCheck` процесса V1 требуется `ActiveProbesAllowed()` — активные проверки прекращаются. |
| Заполнение истории | Единые жёсткие ограничения и адаптивные мягкие ограничения (правила одинаковы, учитывается фактическая нагрузка). |
| Необязательная настройка профиля | **Не входит в это изменение** (YAGNI). |

## Режимы по умолчанию

- Миграция `195_channel_monitor_mode.sql`: если ключ отсутствует, вставляется `'v1'`.
- Если миграция 195 уже применена со старой контрольной суммой, добавляется совместимость контрольной суммы миграции; применённые БД не переводятся принудительно на v1.
- Код: `defaultChannelMonitorMode = v1`; пустые и недопустимые значения нормализуются в v1.
- Значение по умолчанию в форме Settings и резервное значение публичного feature flag при отсутствии или недопустимом значении — v1.
- При пустых settings путь V1 `RunCheck` остаётся **fail-closed** (без проверок) для безопасности тестов; это не зависит от продуктового значения по умолчанию.

## Щадящее заполнение истории (фазы с низким потреблением ресурсов)

### Жёсткие ограничения (для всех серверов)

- Интервал запуска равен `refresh_interval` (60 или 300 секунд). **Для первичного заполнения нет отдельного интервала 5 секунд.**
- Каждый запуск обрабатывает: (1) недавнее перекрытие (примерно 10 минут), затем (2) **не более одного** исторического фрагмента, пока не завершено продуктовое первичное заполнение или обход срока хранения.
- Единственная лидерская блокировка и единый бюджет короткой транзакции (примерно 55 секунд).
- Максимальный размер фрагмента зависит от глубины истории: продуктовые фазы 90m → 1d → 7d → 30d → фоновая фаза 90d.

### Мягкие ограничения (адаптивные)

- Начальный исторический фрагмент: **1 час**; первая инициализация для интерфейса 90m по-прежнему охватывает **2 часа**.
- Минимальный фрагмент: **15 минут**; максимум по глубине: ≤1d → **2 часа**, ≤7d → **4 часа**, более старые данные → **6 часов**.
- После быстрого успешного выполнения размер медленно растёт (×1,5) до максимума для текущей глубины.
- При ошибке или тайм-ауте размер уменьшается вдвое, а ожидание растёт экспоненциально (не более 10 минут).
- Интерфейс показывает уже покрытый диапазон; баннер первичного заполнения отделён от продуктового окна 30d.

### Дедупликация ошибок

- Ветка `request_id IN candidate_ids` ограничивается условием
  `created_at >= $1 - INTERVAL '90 minutes' AND created_at < $2`.

## Вне области изменений

- Принудительное переключение существующего v2 на v1.
- Отдельные workers заполнения истории или read replicas.
- Административная настройка `backfill_profile` (может быть добавлена позднее).
