# Пакетное редактирование JSON в запросах OpenAI

[中文](moego-json-batching.md) | Русский

`openAIRequestView.ApplyPatches` использует `Doc` из `github.com/MoeForge/moego/ojson`, чтобы объединять несколько изменений полей одного запроса и создавать полный результат только один раз в конце. Версия зависимости закреплена на `v0.1.0-alpha.1` (`d016502783037edc58e422331be2b6775d578c13`).

Эта оптимизация не заменяет другие вызовы gjson/sjson, декодирование encoding/json, преобразование протоколов или извлечение данных об использовании. Неизвестные поля, порядок, повторяющиеся ключи, текстовое представление чисел и неизменённый текст защищены дифференциальными тестами на уровне байтов.

## Область применения

Пакетный путь принимает только допустимый JSON-объект, 2–16 изменений скалярных значений и пути из ASCII-идентификаторов глубиной не более четырёх уровней. Корневой объект и каждый исходный родительский объект, через который проходит изменяемый путь, содержат не более 64 членов. Большие `input`, изображения в виде data URL и другое неизменяемое содержимое не исключаются из пакетного пути из-за их размера или числа внутренних полей.

Следующие случаи по-прежнему используют существующую последовательную реализацию sjson: единственное изменение; путь с запросом, индексом или не-ASCII символами; некорректный JSON; строковый родительский узел; пересекающиеся пути родителя и потомка; контейнерные значения или значения с пользовательской сериализацией; объекты с большим числом членов. Это критерии допуска к оптимизации, а не дополнительные правила отклонения запросов.

Ограничение числа членов объекта важно: `Doc` строит временный индекс членов для контейнеров, через которые проходит путь. В эксперименте непосредственное использование `Doc` для объекта размером около 40 KB с 4096 короткими полями дало около 720 KB суммарных выделений памяти против примерно 82 KB у прежнего sjson. Теперь такой объект возвращается к прежней реализации без дополнительного индекса. Предварительная проверка только заимствует исходный ввод и не проверяет уже изменённые родительские объекты через `Doc.Get`, чтобы избежать повторной материализации крупных контейнеров.

## Владение данными и бюджет

- Входное тело нельзя изменять во время вызова; `Doc` и результаты предварительной проверки не сохраняются между вызовами.
- Любая стратегия `ApplyPatches` — пакетный `Doc`, одиночное изменение или последовательный sjson — создаёт отдельный результат и одинаково учитывается в бюджете: перед редактированием резервируется размер входа; при нехватке бюджета запрос отклоняется до любой работы по редактированию. После формирования результата резерв корректируется по его фактическому размеру в обе стороны; при неудаче резерв полностью возвращается. Условия отклонения для пакетных и непакетных запросов одинаковы.
- `Forward` открывает дочерний лимит `WithRequestBodyMemoryScope` для результата каждого patch. Когда новый результат заменяет старый, старый резерв возвращается; при возврате из `Forward` возвращается и резерв последнего результата. Поэтому при повторных попытках с переключением аккаунта переписанные тела не накапливаются до завершения handler. Резерв ingress по-прежнему возвращается существующей функцией освобождения обработчика.
- Этот лимит покрывает результаты patch, а не всю кучу процесса: промежуточные копии последовательного sjson, запасной путь decode+marshal и индекс членов `Doc` отдельно не учитываются. Последний ограничивается описанными выше критериями допуска.
- Если `Doc` отклоняет изменение, используется последовательный sjson. Если и sjson не способен выразить изменение, например установку ключа под массивом, `Forward` повторно применяет ожидающие patch к декодированной map и использует существующий запасной путь marshal, не выполняя тот же пакет patch дважды.
- При исчерпании бюджета функция немедленно возвращает ошибку: она не обходит бюджет другим способом сериализации и не повторяет запрос с другим аккаунтом. Если HTTP-ответ ещё не начат, возвращаются 503 и `Retry-After: 1`; если heartbeat SSE уже отправлен, выдаётся `response.failed`, а в записи ошибки сохраняется ожидаемый статус 503.
- Вызывающая сторона по-прежнему определяет политику отмены и дочитывания данных об использовании от вышестоящего сервиса; функция редактирования не вводит новой семантики ранней отмены.

## Границы совместимости

В дифференциальных тестах вышестоящей alpha-версии под Go 1.27.3 обнаружено отличие байтов результата для ключей пути с некорректным UTF-8: фактический U+FFFD и `\ufffd` имеют одинаковое значение после декодирования, но различаются байтами. Такие пути не попадают в новый пакетный путь. Все структуры и значения с пользовательской сериализацией также остаются на старой реализации, чтобы не менять число вызовов пользовательской сериализации.

## Проверка и бенчмарки

Запускать из `backend`:

```sh
go test -race ./internal/service -run '^(TestOpenAIRequestPatches_|TestOpenAIRequestView_|TestOpenAIGatewayService_OAuthLegacy_UpstreamRequestIgnoresClientCancel)' -count=1
go test -race ./internal/pkg/httputil -run 'Test(ReserveRequestBodyMemory|RequestBodyMemoryBudget)' -count=1
go test -race ./internal/handler -run '^TestOpenAIForwardRequestBodyMemoryOverload' -count=1
go test -race github.com/MoeForge/moego/ojson -run '^TestDoc' -count=1
go test ./internal/service -run '^$' -bench '^BenchmarkOpenAIRequestPatches' -benchmem -benchtime=150ms -count=3 -cpu=1
```

`SequentialSJSON` сохраняет прежнюю последовательную реализацию как базу для бенчмарка и побайтовый oracle. `ApplyPatches` включает проверку допуска к оптимизации и стоимость полной проверки JSON; ни один из этих двух бенчмарков не включает создание request view. Существующий `BenchmarkOpenAIResponses_LargeInputRawPatch`, напротив, включает создание view.

Показатель B/op в отчёте бенчмарка — суммарное число байтов, выделенных за вызов. Его нельзя считать размером удерживаемой кучи или RSS, равно как нельзя непосредственно выводить из него пропускную способность всего сайта, задержку первого токена или время запроса к вышестоящему сервису. Единственное изменение должно сохранять прежнее число выделений; возврат плотных объектов к старому пути добавляет затраты предварительной проверки. У текущего ojson для ARM64 нет пути AVX2, используемого на AMD64; его следует измерять отдельно.

### Измерения 2026-11-03

Go 1.27.3, 150ms × 3 для каждой группы, одно ядро, медиана. На Linux использовался Xeon Skylake с AVX2 и фиксированным CPU; на Mac — Apple M2. Шесть изменений затрагивали модель, reasoning, удаление previous_response_id, предел вывода и service_tier; основное содержимое входа — длинный текст.

| Платформа / вход / число изменений | Прежняя последовательная реализация | Пакетная реализация | Прежние суммарные выделения | Новые суммарные выделения |
|---|---:|---:|---:|---:|
| Linux AMD64 / 1 MiB / 6 | 3.816 ms | 0.756 ms | 6,341,302 B | 1,058,416 B |
| Linux AMD64 / 8 MiB / 6 | 23.162 ms | 5.353 ms | 50,381,747 B | 8,398,448 B |
| Mac ARM64 / 1 MiB / 6 | 2.446 ms | 1.263 ms | 6,341,291 B | 1,058,416 B |
| Mac ARM64 / 8 MiB / 6 | 12.023 ms | 9.290 ms | 50,381,720 B | 8,398,448 B |

При единственном изменении суммарные выделения остались прежними на обеих платформах. После возврата плотного корневого объекта с 4096 полями к прежнему пути на Linux время составило около 170 μs, а суммарные выделения — 82,081 B, примерно как у старой реализации. Предварительная проверка плотного вложенного объекта добавила около 6% времени при прежнем объёме выделений. Три изменения повторяющегося вложенного листового узла выполнялись на Linux примерно в 2.1 раза быстрее, на Mac — примерно на 8% медленнее; на обеих платформах суммарные выделения уменьшились с 3,171,120 B до 1,057,520 B. Выигрыш зависит от входных данных и архитектуры.

Направленные race-тесты связанных сервисов, handler, бюджета и вышестоящего `Doc` прошли; сборка Linux AMD64 и `go vet` также прошли. Установленный локально импортёр golangci-lint 2.13.2 поддерживает export data только до v4 и не может прочитать v5 из Go 1.27.3, поэтому lint не был завершён. `go mod tidy -diff` предложил лишь очистить уже существующие в проекте контрольные суммы старых зависимостей: в этом изменении добавлены только контрольные суммы, необходимые для moego, без несвязанной очистки.

## Оптимизация горячих путей Messages и Responses (2026-11-04)

Эта серия оптимизаций сокращает повторную работу, сохраняя семантику существующих парсеров и обработки совместимости:

- `collectCacheControlPaths` заимствует исходные представления system/messages/tools во время синхронного сканирования; возвращаемые пути и строки логов по-прежнему имеют собственную память. Проверка ограничения числа точек остановки и порядка TTL остаётся двухпроходной, сохраняя прежнее поведение, при котором после удаления повторного ключа становится видимым следующее значение.
- Очистка orphan в OAuth Responses сначала проверяет, может ли потребоваться изменение. При отсутствии вывода инструмента или наличии допустимого `previous_response_id` полное декодирование пропускается; повторяющиеся связанные ключи, экранированные ключи или типы и предполагаемый вывод инструмента по-прежнему проходят через прежний decoder/sanitizer. Предварительная проверка повторно использует существующее сканирование диапазонов байтов, не разворачивая длинный экранированный текст. Прежние проверка допустимости первого массива input, декодирование последнего повторного ключа и ошибки недопустимого JSON или завершающего мусора сохраняются.
- `RequestBodyRef` сохраняет снимок успешно разобранного запроса только для чтения: независимые скалярные строки, протокол и смещения полей, без дополнительных ссылок на старое body. При отсутствии изменений `CloneForBody` и `ReplaceBody` восстанавливают снимок; явный `RequestBodyRef.Replace` делает его недействительным, даже если передан тот же slice. Каждая повторная попытка по-прежнему создаёт отдельный Ref и очищает callback принятия запроса вышестоящим сервисом. Созданные вручную объекты, неудачный разбор и изменения протокола либо body по-прежнему приводят к разбору заново.
- Повторное использование требует не только одинакового начала и длины slice, но и совпадения `maphash`-отпечатка содержимого с отпечатком при разборе. Каждое повторное использование требует одного прохода хеширования, что намного дешевле полного разбора. Если соглашение о неизменяемости нарушено изменением данных на месте, отпечаток приводит к повторному разбору вместо восстановления устаревшей модели, признака потокового режима или смещений полей.

Входное body и результат `Bytes()` заимствуются только для чтения. Нельзя изменять на месте базовую память, пока её удерживает запрос или повторная попытка. Восстановление снимка также перезаписывает временные изменения производных скалярных значений, как это делал прежний повторный разбор. Снимок добавляет немного фиксированных метаданных: это не новый межзапросный кэш, у него нет фонового жизненного цикла и он не удерживает большие body.

Специализированный бенчмарк:

```sh
go test ./internal/service -run '^$' -bench '^(BenchmarkCacheControlPathsLargeContent|BenchmarkOpenAIResponsesOrphanPrecheck|BenchmarkGatewayRequestBodyReuse)$' -benchmem -benchtime=150ms -count=3 -cpu=1
```

`GatewayRequestBodyReuse` начинает измерение после первого разбора запроса и сравнивает clone одной попытки с аккаунтом и два обновления без изменений. `Reparse` принудительно выполняет полный разбор и включает фиксированную стоимость нового снимка, поэтому не является точной базой выделений старого коммита; `Reuse` не означает, что весь запрос больше не нуждается в разборе JSON. `OpenAIResponsesOrphanPrecheck` сравнивает только стадию orphan; прежнюю базу cache_control можно измерить через Go overlay с версией `gateway_claude_oauth_body.go` до изменения.

Среда измерения: Go 1.27.3, Linux AMD64 Xeon Skylake, фиксированное одно ядро, 150ms × 3, медиана:

| Компонент / синтетический вход | Время сравнения | Время после оптимизации | Прежние суммарные выделения | Новые суммарные выделения |
|---|---:|---:|---:|---:|
| cache_control без изменения / 1 MiB | 5.854 ms | 5.119 ms | 2,114,374 B | 476 B |
| cache_control без изменения / 8 MiB | 45.250 ms | 41.575 ms | 16,794,468 B | 476 B |
| Responses orphan / 4 MiB / без previous_response_id | 38.238 ms | 14.168 ms | 28,676,176 B | 10 B |
| Responses orphan / 4 MiB / с previous_response_id | 38.070 ms | 8.252 ms | 28,676,204 B | 6 B |
| Messages: три последующих разбора / 8 MiB / принудительный разбор и повторное использование | 63.068 ms | 0.000234 ms | 840 B | 240 B |

Вход cache_control содержит три фиксированные точки остановки и обычный текст переменной длины; основной выигрыш даёт устранение копирования, а два прохода сканирования остаются. Вход Responses содержит длинный экранированный текст и не требует изменений; после оптимизации для каждого размера получается 0 allocs/op. Небольшие B/op включают амортизированные расходы среды выполнения и не означают нулевых выделений всего шлюза. Строка Messages не включает первый разбор, фактическую обработку совместимости, передачу по сети или генерацию вышестоящим сервисом. Эти результаты не предназначены для вывода о пропускной способности всего сайта.

Строка Messages была измерена до добавления отпечатка содержимого. После его добавления каждое повторное использование требует одного прохода `maphash`: на Apple M2 повторное использование 8 MiB занимает около 2.1 ms (принудительный разбор — около 60 ms), 1 MiB — около 0.26 ms, при прежнем объёме выделений (240 B/op).

Связанные unit/race-регрессии слоя сервисов, регрессии отмены, переключения и бюджета в handler, итоговая повторная проверка граничных случаев с race, `go vet` и компиляция программы бенчмарков Linux прошли. Репозиторный fuzz выполнил 1,393 успешные итерации; isolated fuzz с исходными функциями, без изменений извлечёнными во временный модуль, выполнил 34,363 успешные итерации за 15 секунд. `golangci-lint` по-прежнему заблокирован несовместимостью инструментов: Go 1.27.3 использует export data v5, а текущий импортёр поддерживает лишь v4.
