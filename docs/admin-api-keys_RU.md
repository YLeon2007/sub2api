# Административные API-ключи с ограниченными правами

[中文](admin-api-keys.md) | Русский

Ограниченные административные ключи предназначены для автоматизированного управления заданными ресурсами. Они отличаются от пользовательских API-ключей для вызова моделей и не равнозначны сеансу входа администратора. Ключ передаётся в заголовке `x-api-key`. Доступны только интерфейсы и операции, явно зарегистрированные в каталоге разрешений; новые интерфейсы не наследуют права автоматически.

## Создание и настройка

Войдите как администратор и откройте раздел ключей доступа администратора в «Системные настройки → Безопасность». Создание доступно только после успешной загрузки каталога разрешений и групп.

1. Укажите название, примечание, срок действия и разрешённые IP/CIDR. Срок задаётся по местному времени; пустое поле означает отсутствие срока истечения. Пустой список IP означает отсутствие ограничений по IP-адресу источника.
2. Добавьте правила ресурсов, отдельно выбрав операции, группы, типы аккаунтов и платформы. В новом правиле ни операции, ни типы аккаунтов не выбраны; все глобальные разрешения также отключены.
3. При необходимости отдельно включите глобальные разрешения. После сохранения сразу скопируйте полный ключ: он возвращается только в текущем ответе на создание или ротацию. После закрытия окна прочитать его заново из списка нельзя.

Создание, обновление, отключение/включение, ротация, отзыв и удаление записи используют действующий механизм дополнительной проверки. Появление запроса проверки зависит от настроек step-up и текущего состояния авторизации. Интерфейсы жизненного цикла ключей принимают только JWT-сеанс администратора: ограниченный ключ не может управлять собой или создавать другие административные ключи.

Если существует старый ключ с полными правами, страница показывает сворачиваемый раздел совместимости, где его можно ротировать или удалить. Создавать новые старые ключи с полными правами через страницу больше нельзя; переведите автоматизацию на ограниченные ключи.

## Как сопоставляются правила аккаунтов

Для одной операции над аккаунтом внутри одного правила должны одновременно выполняться все условия (AND):

- Операция присутствует в `permissions`.
- Тип аккаунта присутствует в `account_types`. Пустой список означает отсутствие прав на операции с аккаунтами, а не разрешение всех типов.
- Список `platforms` пуст либо содержит платформу аккаунта.
- Для аккаунта с группами совпадает хотя бы одна выбранная группа либо включено `all_groups`. Для аккаунта без групп необходимо явно включить `include_ungrouped`.

Между правилами действует OR: достаточно одного правила, целиком разрешающего операцию. Нельзя объединить тип аккаунта из одного правила с группой или платформой из другого, чтобы получить разрешение. Для каждой операции требуемые права проверяются отдельно: запись учётных данных, изменение сетевых настроек, статуса, параметров планирования, моделей и связей с группами не входят в право «изменять название и примечание».

`all_groups` охватывает и будущие группы, но не включает автоматически аккаунты без групп. Каждая целевая группа при создании аккаунта, а также каждая добавляемая или удаляемая группа при изменении связей должны дополнительно пройти проверку группы для соответствующей операции.

**Общий для нескольких групп аккаунт остаётся одним ресурсом.** Если аккаунт связан с несколькими группами, совпадения с одной разрешённой группой может быть достаточно для выполнения разрешённой операции над аккаунтом. Изменение учётных данных или статуса, обновление токенов и удаление влияют на все группы, использующие этот аккаунт. Интерфейс явно предупреждает об этом; учитывайте совместное использование при выдаче прав. Ответ для ограниченного ключа содержит только разрешённые для чтения связи с группами и не означает отсутствия других связей.

## Модели группы — реальное ограничение допуска

`groups.models.read` и `groups.models.write` — независимые разрешения в правилах ресурсов. Они проверяются по группе и платформе внутри одного правила. Тип аккаунта не ограничивает настройку всей группы; выдавать одновременно права на операции с аккаунтами или глобальные разрешения не требуется.

Здесь изменяется `model_allowlist`, применяемый при обращении к вышестоящему сервису: он влияет на доступные для вызова модели всей группы, а не только на отображение списка в интерфейсе. Интерфейс записи принимает исключительно `model_allowlist`; через него нельзя изменить тарифные коэффициенты или другие настройки группы. При наличии только права чтения моделей группы ответ содержит лишь ID, название, платформу и список разрешённых моделей. Для чтения полной конфигурации группы требуется глобальное разрешение `groups.read`.

Для чтения моделей-кандидатов конкретной группы необходимо право чтения этой группы либо глобальное `groups.read`. Для чтения кандидатов по умолчанию (ID группы `0`) требуется отдельно выданное `models.defaults.read`.

## Глобальные разрешения и границы ответов

`global_permissions` не зависят от правил ресурсов и не ограничиваются выбранными группами или типами аккаунтов. Например, `users.read`, `dashboard.read` и `payment.read` открывают соответствующие данные всего сайта. Выбор группы не сужает эти разрешения до её данных; в обратную сторону выбор группы не предоставляет их автоматически.

Каталог разрешений регистрирует точные сочетания интерфейса и HTTP-метода. Сейчас нет разрешения `payment.mark_paid` и разрешения на предварительный просмотр возврата. Другие разрешения — на возврат, отмену заказа или повторное исполнение — не заменяют эти действия.

Состав ответов для ограниченных ключей сужен в соответствии с назначением:

- Чтение аккаунта возвращает основные данные управления и сопоставление моделей, но не OAuth-токены, API-ключи, произвольные `extra` или полные учётные данные. `accounts.credentials` разрешает запись и не даёт возможности читать учётные данные.
- Кандидаты прокси содержат ID, название, протокол, хост, порт, статус и срок действия, но не имя пользователя или пароль для аутентификации прокси.
- Профиль пользователя формируется по белому списку полей. Для контактных данных требуется `users.read`, для полей баланса — `users.balance.read`, для полей конфигурации групп — `groups.read`. В ответ пользователя не включаются связанные подписки и данные использования: они доступны через собственные интерфейсы и разрешения.
- Ответ подписки не включает вложенные данные пользователя, назначившего администратора или полную группу. Если выдано только право записи подписок или квот платформ, успешный ответ подтверждает лишь ID ресурса, не раскрывая данные, требующие отдельного права чтения.
- Записи использования содержат только использование самого запроса, снимок тарификации и связанные ID; в них не включаются пользовательский API-ключ, учётные данные аккаунта или финансовые данные пользователя. История использования промокодов и чтения объявлений также возвращает только поля записи и ID пользователя.
- Для чувствительных эксплуатационных данных, в том числе подробностей ошибок запросов, нужны отдельные разрешения. Глобальные разрешения чтения всё равно могут раскрывать конфиденциальные деловые данные: выдавайте только то, что действительно необходимо задаче.

## Хранение, ротация и отзыв ключей

Полный ключ генерируется из случайных байтов. База данных хранит его SHA-256-дайджест и префикс для отображения и поиска, но не полный ключ, который можно было бы показать повторно. На стороне клиента храните ключ в менеджере секретов или секретной переменной среды выполнения.

Отключённый ключ можно включить снова. Ключ с истёкшим сроком действия или не подходящим под разрешённые IP источником не проходит аутентификацию. Ротация немедленно делает старый ключ недействительным и однократно возвращает новый. Постоянный отзыв необратим. Удалить запись из списка можно только после отзыва: удаление скрывает её из списка управления, но сохраняет историю операций.

Если при редактировании срок действия не менялся, интерфейс сохраняет исходное значение сервера, чтобы не обрезать секунды, микросекунды или информацию о часовом поясе.

## Поиск и автоматический выбор прокси

`proxies.read` — глобальное разрешение, отдельное от `accounts.network`. Первое позволяет получать безопасные сведения о кандидатах прокси; второе управляет адресом подключения, прокси и параметрами соединения для разрешённых аккаунтов.

- `GET /api/v1/admin/proxies` принимает `page`, `page_size` и `search`. Размер страницы по умолчанию — 50, максимум — 100.
- `GET /api/v1/admin/proxies/all` для совместимости с клиентами возвращает массив. При явно заданных параметрах пагинации выполняется постраничный запрос; информация о страницах передаётся в заголовках `X-Total-Count`, `X-Page`, `X-Page-Size` и `X-Total-Pages`.
- Без параметров пагинации `/proxies/all` при каждом запросе заново выбирает случайную выборку не более 50 кандидатов из всего пула, не исключая прокси, уже используемые аккаунтами. Ответ содержит `Cache-Control: no-store`.
- `ids` позволяет повторно получить выбранные прокси: не более 100 различных ID за запрос. Существующие записи возвращаются в порядке запроса.

Запись аккаунтов ограниченными ключами и импорт Codex поддерживают `proxy_mode`: `direct` (прямое подключение), `specified` (положительный `proxy_id`), `random` (случайный выбор), `least_used` (наименее используемый). Автоматический выбор выполняется сервером внутри транзакции записи аккаунта из включённых прокси с неистёкшим сроком действия. Если доступных прокси нет, операция завершается ошибкой. В автоматическом режиме нельзя одновременно указывать положительный `proxy_id`. Старое поле `random_proxy: true` совместимо со случайным режимом, но не должно конфликтовать с другими режимами. Запрос случайных кандидатов и автоматический выбор при записи — два независимых действия.

## Импорт сеансов Codex

Ограниченный ключ может использовать `POST /api/v1/admin/accounts/import/codex-session`, но не переключается на процедуру импорта администратора с полными правами.

- Необходимо явно передать `group_ids`. Новый аккаунт всегда создаётся с платформой `openai` и типом `oauth`; каждая целевая группа проверяется отдельно.
- Для создания нужны `accounts.create`, `accounts.credentials` и `accounts.schedule`. При обновлении найденного аккаунта заново проверяются текущий ресурс и соответствующие права записи. Изменение связей дополнительно требует `accounts.groups`.
- Для `base_url`, прокси, отпечатка клиента или параметров WebSocket требуется `accounts.network`; для `model_mapping` — `accounts.models.write`.
- В `credential_extras` разрешены только `base_url` и `model_mapping` с отдельной проверкой прав. В `extra` доступны лишь зарегистрированные параметры отпечатка Codex и WebSocket. Произвольная передача полей и обход проверки рисков смешанных каналов не поддерживаются.
- При импорте кандидаты ищутся только в разрешённой области по идентификационным данным текущего элемента. Ответ не раскрывает их учётные данные. При обновлении существующего аккаунта идентификационные данные и права повторно проверяются на этапе записи.

## Примеры API

Все домены, ключи, JWT, ID и содержимое сеансов ниже — заполнители. Успешные ответы используют действующую в системе общую оболочку ответа.

Создание ограниченного ключа в сеансе администратора (если система требует step-up, сначала выполните текущую процедуру дополнительной проверки):

```bash
curl 'https://example.invalid/api/v1/admin/settings/admin-api-keys' \
  -H 'Authorization: Bearer <ADMIN_JWT>' \
  -H 'Content-Type: application/json' \
  --data '{
    "name": "Инструмент чтения OAuth",
    "description": "Чтение OpenAI OAuth аккаунтов выбранной группы",
    "enabled": true,
    "expires_at": null,
    "allowed_ips": ["192.0.2.10/32"],
    "policy": {
      "rules": [{
        "permissions": ["accounts.read"],
        "group_ids": [123],
        "all_groups": false,
        "include_ungrouped": false,
        "account_types": ["oauth"],
        "platforms": ["openai"]
      }],
      "global_permissions": []
    }
  }'
```

Чтение аккаунтов с ограниченным ключом:

```bash
curl 'https://example.invalid/api/v1/admin/accounts?page=1&page_size=20' \
  -H 'x-api-key: <SCOPED_ADMIN_KEY>'
```

Отдельное обновление списка разрешённых моделей группы после выдачи `groups.models.write` для выбранной группы:

```bash
curl -X PUT 'https://example.invalid/api/v1/admin/groups/123' \
  -H 'x-api-key: <SCOPED_ADMIN_KEY>' \
  -H 'Content-Type: application/json' \
  --data '{"model_allowlist":{"enabled":true,"models":["<MODEL_ID>"]}}'
```

Создание Codex OAuth аккаунта со случайным выбором прокси сервером после выдачи необходимых для импорта разрешений:

```bash
curl 'https://example.invalid/api/v1/admin/accounts/import/codex-session' \
  -H 'x-api-key: <SCOPED_ADMIN_KEY>' \
  -H 'Content-Type: application/json' \
  --data '{
    "content": "<CODEX_SESSION_CONTENT>",
    "name": "Импортированный аккаунт",
    "group_ids": [123],
    "update_existing": false,
    "proxy_mode": "random"
  }'
```

Интерфейсы жизненного цикла находятся в `/api/v1/admin/settings/admin-api-keys`: `GET` — список и каталог разрешений, `POST` — создание, `PUT /<KEY_ID>` — обновление, `POST /<KEY_ID>/rotate` — ротация, `DELETE /<KEY_ID>` — постоянный отзыв, `DELETE /<KEY_ID>/record` — удаление отозванной записи. Запрос обновления содержит полную конфигурацию и политику; отсутствие поля не означает сохранение его прежнего значения, как при PATCH.
