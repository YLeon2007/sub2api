# Локальный протокол плагинов Sub2API

[中文](README.md) | Русский

Этот каталог — публичный контракт, на который могут опираться разработчики плагинов. `v1/plugin.proto` и `v1/runtime.go` описывают процессный протокол, `v1/manifest.schema.json` задаёт схему манифеста пакета, а `docs/` фиксирует правила разработки и публикации. Приватные реализации provider-ов не должны находиться в этом каталоге.

## Сущность и способ запуска

Плагин поставляется как файл `.s2plugin`: ZIP-пакет с манифестом, подписью, независимыми исполняемыми файлами и статическим UI. Администратор вручную загружает его на отдельной странице управления плагинами. Sub2API не скачивает плагины из сети автоматически и не требует Docker.

После включения Sub2API запускает бинарь для текущей ОС и архитектуры как дочерний процесс и передаёт запросы/ответы по локальному gRPC stream. При выходе процесса плагина Sub2API очищает его; при отключении плагин сначала перестаёт принимать новые запросы и затем ждёт завершения уже обрабатываемых.

Многоинстансные установки не обязаны иметь общий каталог плагинов. Host сохраняет в базе исходный пакет, уже прошедший проверку подписи; если конкретному инстансу не хватает локальных файлов, он заново проверяет подпись и распаковывает пакет, а также периодически синхронизирует включённое состояние, процент rollout-а и зашифрованную конфигурацию. Все инстансы должны использовать одну базу данных и одинаковый ключ шифрования.

Отдельный процесс — это граница кода и поставки, но не полноценная ОС-песочница. Плагин получает файловые и сетевые права пользователя сервиса Sub2API, поэтому устанавливайте только подписанные пакеты доверенных издателей. Закрытый бинарь усложняет распространение исходников, но не обещает невозможность реверс-инжиниринга.

## Начальная граница возможностей

Сейчас принимается только capability `openai.oauth.outbound_transport.v1`:

- совпадают только upstream HTTP-запросы с `platform=openai` и `account_type=oauth`;
- API Key аккаунты, другие provider-ы, OAuth login и token refresh не проходят через плагин;
- плагин устанавливает настоящее upstream HTTP/TLS-соединение и возвращает исходный HTTP-ответ;
- OAuth WebSocket аккаунты, попавшие в плагин, используют существующий HTTP Bridge Sub2API, чтобы не обходить HTTP-протокол плагинов v1;
- Sub2API по-прежнему отвечает за обработку статуса ответа, SSE parsing, mapping ошибок, учёт usage, billing и downstream output;
- rollout процент стабильно бакетируется по ID аккаунта, а не попавшие в rollout OAuth аккаунты продолжают использовать встроенный путь.

## Host service (HostService)

`HostService` — общий слой возможностей, который host предоставляет плагину через обратный go-plugin broker. Он не зависит от конкретного типа плагина и предназначен для stateful plugins. Согласование выполняется через `TransportPlugin.InitHostServices`: после запуска host передаёт plugin-у broker stream id, а plugin подключается обратно и получает `HostServiceClient`.

- **Опционально и обратно совместимо**: старый plugin без `InitHostServices` возвращает `Unimplemented`; host молча пропускает этот вызов, и forwarding не меняется. У host service есть отдельный `HostServiceAPIVersion`; новые возможности не меняют transport contract и не ломают существующие plugins.
- **Жизненный цикл процесса**: экземпляр host service связан с жизненным циклом plugin process. При выходе plugin broker закрывается и автоматически выполняет `GracefulStop`; ручная очистка со стороны plugin не требуется.

Доступные общие facilities:

- **Namespace key-value storage (KV)**: `KVGet` / `KVSet` / `KVDelete` / `KVList` для сохранения plugin state между запросами, replica и перезапусками. Хранилище работает через Redis, поэтому в multi-instance deployment состояние естественно общее.
  - **Изоляция namespace**: host добавляет identity plugin-а (`pluginKey`) для этого runtime connection; plugin не может подменить identity и читать или изменять namespace другого plugin.
  - **Ограничения**: `namespace` / `key` допускают только `[A-Za-z0-9._-]`; размер одного значения — до 256 KiB; `ttl_seconds=0` означает отсутствие срока, положительное значение ограничено сверху; количество результатов `KVList` также ограничено.

При добавлении новой host facility достаточно добавить RPC в `HostService`; transport contract и формат manifest менять не нужно.

## Структура пакета

```text
manifest.json
signature.json                 # обязателен для production-пакета
runtimes/linux-amd64/plugin
runtimes/linux-arm64/plugin
runtimes/windows-amd64/plugin.exe
ui/index.html
ui/assets/...
```

`manifest.json` обязан перечислять SHA-256 всех runtime- и UI-файлов. `signature.json` подписывает точные байты `manifest.json` Ed25519 private key доверенного издателя. Официальный публичный ключ OpenAI Transport встроен в host; публичные ключи сторонних издателей добавляются оператором в `plugins.trusted_publishers`. Хэши файлов защищены подписанным манифестом.

По умолчанию плагин остаётся отключённым. Неподписанные пакеты по умолчанию отклоняются; `plugins.allow_unsigned` предназначен только для локальной отладки собственных сборок.

## Совместимость

Манифест должен одновременно объявлять:

- `requires.sub2api`: допустимый SemVer-диапазон Sub2API;
- `requires.recommended_sub2api_version`: рекомендованную версию host-а;
- `requires.tested_sub2api_versions`: версии host-а, реально проверенные издателем;
- `plugin_protocol`, `transport_api`, `ui_bridge`: три независимые версии протокола.

Если версия host-а вне диапазона, плагин можно установить и просмотреть, но он остаётся в состоянии «несовместим» и не включается. Если версия входит в диапазон, но не перечислена как протестированная, администратор должен дополнительно подтвердить включение.

## UI isolation и Bridge

UI плагина — статические файлы из пакета. Host загружает их в sandbox iframe только с `allow-scripts`. iframe не содержит администраторского Token и не может напрямую обращаться к Admin API. При каждом открытии страницы настроек host выдаёт краткоживущий URL ресурсов и отдельный Bridge Token, проверяя одновременно окно-источник и Token сообщения.

UI может отправлять следующие сообщения. Они разделены по смыслу, а требования к авторизации и side effects согласованы: read operations не требуют повторной проверки, write и active test — требуют; любой plugin может переиспользовать этот набор, он не привязан к конкретной реализации:

| Сообщение | Смысл | Повторная проверка | Plugin RPC |
| --- | --- | --- | --- |
| `config.load` | чтение сохранённой конфигурации | нет | host database |
| `config.save` | запись конфигурации | да | `ValidateConfig` + `ApplyConfig` |
| `config.test` | активная проверка конфигурации/соединения (может иметь side effect) | да | `TestConfig` |
| `plugin.status` | чтение runtime status без side effect | нет | `Health` (`status_json`) |
| `ui.resize` / `ui.notify` | только UI-взаимодействие | — | — |

Каждый запрос содержит `request_id`; host отвечает результатом `<type>.result`.

- Конфигурация целиком шифруется ключом Sub2API и сохраняется в базе; работающий plugin сначала валидирует и применяет новую конфигурацию, а при ошибке записи в БД возвращает старую.
- Результат `config.test` plugin UI показывает самостоятельно — inline или через `ui.notify`; host больше не обязан принудительно показывать успешный результат, чтобы polling не превращался в поток уведомлений.
- `plugin.status` — общий **read-only** канал runtime status. Host вызывает `Health` работающего plugin через `GET /admin/plugins/:id/status` и возвращает `{healthy, message, status_json}`. `status_json` — непрозрачный JSON snapshot plugin-а: host его не разбирает и не использует для health decision. Plugin обязан формировать его без side effects: не применять конфигурацию, не обращаться к upstream и не запускать probes. Поэтому endpoint только для чтения и не требует повторной проверки. Если plugin не запущен, возвращается `healthy=false` без `status_json`.

## Исходники протокола

- `v1/plugin.proto`: стабильное определение межпроцессных сообщений.
- `v1/runtime.go`: Go entrypoint процесса плагина и декларация host client.
- `v1/manifest.schema.json`: JSON Schema для `manifest.json`.

Плагины взаимодействуют через процессный протокол, не используют Go dynamic linking и не требуют совпадения компилятора или shared-memory ABI с Sub2API.
